# ADR-0016: Contract-first API, generated client and drift checks

## Context and Problem Statement

[ADR-0012](0012-technology-stack.md) states that the backend is checked
against `openapi.yaml` and that the frontend client is generated from it, but
not how. Release 1 requires the contract to match the implementation.
How is the contract kept in sync with both sides, and how does the SPA talk
to the API in development?

## Decision Drivers

* `openapi.yaml` must match the implementation (completion criterion).
* Minimal tooling; works from a clean clone with Java 21, Node and Docker.
* Session cookies and CSRF must work without cross-origin complexity.

## Considered Options

* Contract-first: hand-written `openapi.yaml` is the source of truth
* Code-first: springdoc generates the document from controllers
* Client generators: `openapi-typescript` + `openapi-fetch`, orval,
  openapi-generator (typescript-fetch)

## Decision Outcome

Chosen option (accepted after release 1 was implemented and verified with
it):

* **Contract-first.** `openapi.yaml` is edited first; lint with
  `npx --yes @redocly/cli@latest lint openapi.yaml` (config `redocly.yaml`).
* **Frontend:** types generated by `openapi-typescript` into
  `frontend/src/api/schema.d.ts`, calls made with `openapi-fetch` through one
  client module that adds the `X-XSRF-TOKEN` header and maps `401` to the
  sign-in redirect. A check script regenerates the types and fails if
  `git diff --exit-code` shows drift.
* **Backend:** MockMvc integration tests validate responses against
  `openapi.yaml` (Atlassian `com.atlassian.oai:openapi-request-validator-mockmvc`
  3.0.0, the renamed successor of `swagger-request-validator-mockmvc`). It
  loads the OpenAPI 3.1 contract (verified in Increment 2) and validates the
  auth requests and responses since Increment 3; fallback: validate response
  bodies against the component schemas with a JSON Schema validator.
* **Development topology:** the Vite dev server (port 5173) proxies `/api`
  to Spring Boot (port 8080 by default, `MATRIZ_API_PORT` in `.env`), so the browser sees one origin and no CORS
  configuration is needed. PostgreSQL runs on port 5432 (overridable in
  `.env`).

### Consequences

* Good, because the contract is reviewed before code and drift fails a check.
* Good, because `openapi-fetch` is tiny and fully typed, with no generated
  runtime code to maintain.
* Neutral, because backend DTOs are hand-written and must follow the contract
  (enforced by the validation tests).
* Bad, because a production deployment would need a reverse proxy or Spring
  Boot serving the built SPA (hosting is still pending).

### Confirmation

Redocly lint passes; frontend `npm run api:check` passes; backend contract
tests pass in `./mvnw verify`. Release 1 confirmed this: every MockMvc API
test checks requests and responses against `openapi.yaml` (one known
validator gap for comma-separated array query parameters, covered by
`TaskApiTests`; see [`verification.md`](../verification.md) §5).

## Pros and Cons of the Options

### Contract-first

* Good, because the contract is the agreed artefact of the project.
* Bad, because DTOs are written twice (YAML and Java) — mitigated by tests.

### Code-first (springdoc)

* Good, because no duplication.
* Bad, because the contract would follow the code instead of driving it.

### orval / openapi-generator

* Neutral, because they generate more code (hooks/classes) than needed.
